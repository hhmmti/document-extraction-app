# esp_design_extraction

The extraction core of the design-document pipeline described in `design-note.md`. This folder holds its first three stages, *Detect*, *Prep* and *Extract* (Round 1 → Stages), and the transform of *Validate and stage*. Detect, Prep and stage are deterministic: no AWS, no network, no model. Every stage takes its input in memory and writes nothing to disk.

- `extraction.detect(pdf_bytes)` returns a `Detection`: the vendor family, the page count, and each page's resolved roles. Its `UNKNOWN_TEMPLATE` error names the near misses (each family with some of its page-1 markers: how many, and the required pages found) and the PDF producer, never document text.
- `extraction.prep(pdf_bytes, detection, source_file="")` returns a `PrepResult`: the kept original page numbers, the layout text for each kept page with the private-use glyphs translated, and one manifest row per source page.
- `extraction.assemble.assemble_prompt(family, prep_result, source_file, well_id=None, extraction_date=None, clarifications=True)` returns the extraction prompt. By default it adds each family's approved contract clarification (`extraction/assets/amendments/f<n>.md`; today F2, a clarification and revision for its newer report generator awaiting approval, and F3, F5 and F7) after the contract; with `clarifications=False` it is byte for byte what the per-family batch runners built, which the corpus byte check tests, except that a file name containing `&` is now substituted literally: the runners' `sed` put placeholder text in its place, and the byte check carries one allowance for the two corpus documents that hit this. Its inputs are the verbatim copies in `extraction/assets/`, whose hashes are in `assets/MANIFEST.txt`.
- `extraction.bedrock.extract(prompt, budget_s=..., max_tokens=..., model_id=..., effort="medium", client=None)` makes one streaming Converse call to Opus on Bedrock, with adaptive thinking at the given effort, no retries, and bounded by `budget_s`. It returns the report text and, separately, any reasoning text; the stop reason, token counts, time to first token, total model time, model id and the prompt's SHA-256.
- `extraction.stage.stage(report_text, organization_id, well_id, family, evidence)` turns one report into the three load grains (`pump_config`, `esp_well_design_context`, `curve_observations`, as object-dtype DataFrames), the per-document log (`reconciliation`, `d16_log`, `d17_log`, `gas_log`, `d16_tier_a_fallback`, `unit_conversions`) and the quarantine rows. It is the corpus batch loader's per-document transform, copied with its logic unchanged; `extraction/stage/MANIFEST.txt` has the hashes and every edited line. `family` is the code Detect assigned; if the report's `vendor_family` names another family it raises `FAMILY_MISMATCH`. Organisation and well come from the caller; `well_id=None` is an unmatched well, which gets quarantine and reconciliation rows and no load rows. `evidence` is the alias evidence: `corpus_evidence(report_texts)` learns it from every report in the order given, as the batch loader did; `production_evidence(report_text)` is the frozen corpus evidence (`alias-evidence-v1.json`, rebuilt only as a new version by `scripts/freeze_alias_evidence.py`) plus the report's own, learned last. Four data assets are not kept here: that file, the D31 seed `m2-d31-seed-aliases.csv`, the pump catalogue snapshot `universal_catalog.parquet` (unknown models) and the field inventory `m1-field-inventory.csv` (prompt assembly). They are read from the directory `ESP_EXTRACTION_ASSETS_DIR` names, and each must match the SHA-256 in `extraction/stage/MANIFEST.txt` (the inventory: `extraction/assets/MANIFEST.txt`) or reading it raises `ASSET_INVALID`.
- Staging also validates. `stage(..., detection=None, prep=None)` takes the run's Detect and Prep results as keyword arguments; the rules that read page roles or page text, and per-value grounding, are not evaluated without them and say so in `notices`. Before staging, three structure guards (frontmatter, the five `stg_*` blocks, a parseable `row_counts` footer) raise `REPORT_INVALID`, and nothing is staged. After staging, `extraction/validate/` adds five fields to the result: `findings`, `unknown_models`, `review`, `notices` and `spec_validation_status`. Their rules, guards and signals are the approved design sheet's; the rule list is `extraction/validate/rules.py`. Record shapes:
  - **finding**: `rule_id`, `spec_severity` (the validator spec's, or null for a guard it does not have), `round1_severity` (`REPORT_INVALID` for the structure guards, `LOAD_HALTED` for D17, `EXTRACTION_EMPTY` for G-E1, otherwise `warning`), `scope`, `table`, `row_key` (the row's 1-based position in its `stg_*` block, or null), `column`, `value`, `message`, `blocks_publish` (true for V-08 and D17).
  - **review**, one per in-scope staged value: `field`, `table`, `row_key`, `value`, `cited_page`, `grounding` (`cited_page`, `other_page`, `not_found` or `not_evaluated`), `reasons` (one string per signal that fired: `grounding`, `rule`, `conflict`, `quarantined`, `known_issue`, `frequency_trap`, `expected_missing`), `needs_review`. Where no page is cited, `other_page` means found on some kept page and is not a reason. A conflict row gives one item, on its model field (or on `extraction_status` where the row has none); it is `conflict_benign`, informational and not needing review, when both printed forms resolve through D31 to the same canonical model. Never-printed fields (staging vocabulary and metadata such as `extraction_status` and `source_page`) are never grounded. A field the family prints in every corpus report but this report does not stage gets a record with `row_key` and `value` null.
  - **unknown model**: `model`, `class` (`unresolved`, `absent`, `ambiguous` or `no_head_curve`, against the catalogue), `pump_model_as_printed`, and `candidates` when ambiguous. Each row's D31 name, or its printed string where D31 gave none, goes through the one catalogue lookup (`extraction/catalogue.py`): exact, then case-insensitive, then the upper-case letters-and-digits key, a case or key match taken only when it names exactly one catalogue name. The grains keep D31's name.
  - **notice**: `kind` (`known_issue` or `not_evaluated`), `rule_id`, `family`, `field`, `message`.
  - `spec_validation_status` follows the spec's §1.2: any HALT finding gives `failed`, any ERROR or WARN `needs_review`, otherwise `passed`.
  - Three emptiness guards the spec does not have set a floor on it. G-E1, no `stg_pump_config` and no `stg_design_context` rows, is `failed`, and the run fails `EXTRACTION_EMPTY` with the report, findings and review stored; its message names the rule ids of any halt the model declared, never document text. G-E2, no pump rows beside other rows, and G-E3, a halt the model declared that still left rows, are at least `needs_review`, each with one review item (`no pump rows extracted`, `model halt: <rule>`). A declared halt is a prose line starting `HALT` and a separator or rule id, or `validation_status: failed` in the frontmatter. The no-pump-rows notice names its reason: unmatched well, empty extraction, no pump rows extracted, or a model halt.
- Each failure raises `extraction.ExtractionError`, which carries `code`, `message` and `details`. The codes are `IMAGE_ONLY`, `UNKNOWN_TEMPLATE`, `AMBIGUOUS_TEMPLATE`, `REQUIRED_PAGES_MISSING`, `PREP_FAILED`, `GENERIC_TOO_LARGE`, `MODEL_TIMEOUT`, `MODEL_TRUNCATED`, `MODEL_ERROR`, `FAMILY_MISMATCH`, `ASSET_INVALID`, `REPORT_INVALID`, `EXTRACTION_EMPTY`, `LOAD_HALTED` and `STORE_FAILED`. The Lambda (`lambda_function.py`) adds `INTAKE_INVALID` and `INTERNAL_ERROR`.

The signatures, page maps and glyph map are in `extraction/families.py`. The parity comparator is `extraction/compare/parity.py`; it parses values with the loader's `values.py`, copied verbatim beside it (hash in `extraction/compare/MANIFEST.txt`), and prices calls from `extraction/compare/pricing.json`.

## Tests

```bash

.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest              # unit tests; corpus tests skip; no AWS
```

The stage tests and the prompt-assembly tests also need `ESP_EXTRACTION_ASSETS_DIR`; without it they skip.

The corpus tests check detection and prep parity against the output of the corpus slicing step this code was ported from, and check that assembled prompts match the ones the batch runners saved. They run with `-m corpus` and need these environment variables:

| Variable | Points at |
|---|---|
| `ESP_CORPUS_DIR` | the directory of source design documents |
| `ESP_PREP_REF_DIR` | the slicing step's output directory, holding `prep-manifest.csv` and `text/<family-slug>/<stem>/p<n>.txt` |
| `ESP_BATCH_PROMPT_DIR` | the runners' saved prompts, `<stem>.prompt.txt`; the prompt byte check skips without it |

```bash
export ESP_CORPUS_DIR="<corpus dir>"
export ESP_PREP_REF_DIR="<reference output dir>"
export ESP_BATCH_PROMPT_DIR="<saved prompts dir>"
.venv/bin/python -m pytest -m corpus
```

Every expected value is read from the manifest at run time. A full corpus run takes several minutes.

## Parity run

Six documents, one per family, rerun through the new path and compared with the old batch reports. The scripts find them in the corpus directory by the SHA-256 of the PDF (`PARITY_DOCS` in `extraction/compare/parity.py`), so no document name is kept here. In run order, shortest assembled prompt first:

| # | Family | Selection | PDF SHA-256 (prefix) | Prompt bytes | Kept pages |
|---|---|---|---|---|---|
| 1 | F4 | pilot brief's pick | `d630530e4b6b` | 132,270 | 5 |
| 2 | F5 | pilot brief's pick | `e073658133bc` | 151,786 | 7 |
| 3 | F2 | pilot brief's pick | `c55ecf1b0789` | 153,762 | 9 |
| 4 | F3 | pilot brief's pick | `bb366c921b50` | 156,093 | 7 |
| 5 | F7 | pilot brief's pick (the family's only document) | `83cc3aefeb0a` | 203,492 | 16 |
| 6 | F1 | the longest document | `1ad7b6c31418` | 322,766 | 34 |

`scripts/parity_run.py` calls STS and Bedrock; run it by hand. It keeps the account preflight, refuses an output directory inside this folder (outputs hold client data), and will not rerun a document whose `run.json` records a completed run unless given `--force`. Per document it writes `<out>/<stem>/report.md`, `run.json` (tokens, time to first token, model time, output tokens per second, stage durations, prompt and report bytes, bytes per output token, stop reason, share of `max_tokens`) and, when the stream carries reasoning text, `reasoning.txt`. Defaults: `--max-tokens 128000`, `--budget-s 1800`, effort `medium`.

`scripts/parity_compare.py` is deterministic and makes no calls. It compares each new report with the old one and writes `<out>/parity_report.md`: the verdict table, metrics and cost, the timing verdict, the F1 old-input check, and every difference.

```bash
aws sso login --profile roam-ai
export ESP_CORPUS_DIR="<corpus dir>"
export ESP_OLD_REPORTS_DIR="<old batch reports dir>"
export ESP_BATCH_PROMPT_DIR="<saved prompts dir>"
AWS_PROFILE=roam-ai .venv/bin/python scripts/parity_run.py --doc all --out /tmp/esp-parity
.venv/bin/python scripts/parity_compare.py --out /tmp/esp-parity
```

`--doc` also takes one stem, or family codes such as `F1,F3,F5` for those families' parity documents. `--effort high` sends `output_config.effort = high` and records it in `run.json` (the default is `medium`). Contract clarifications are on by default: each family's approved clarification (`extraction/assets/amendments/f<n>.md`; today F2, a clarification and revision for its newer report generator awaiting approval, and F3, F5 and F7) goes in as a `# ===== CONTRACT CLARIFICATIONS: <contract> =====` block after the contract and before the report contract, and `run.json` records that they were on and each clarification's SHA-256. `--no-clarifications` sends the batch runners' prompt byte for byte. `smoke_extract.py` takes the same flag. Cost stays `pending` until both prices in `pricing.json` are filled in from the AWS Bedrock pricing page.

### High-effort rerun and gate re-check

Rerun the failing families at effort `high`, compare the new run with the old reports and with the medium run, then re-check the gate fields the adjudicated worksheet marked wrong. Only the first command calls AWS.

```bash
aws sso login --profile roam-ai
export ESP_CORPUS_DIR="<corpus dir>"
export ESP_OLD_REPORTS_DIR="<old batch reports dir>"
MEDIUM="<medium parity run dir>"   # holds the adjudicated adjudication.csv
HIGH="<high parity run dir>"
AWS_PROFILE=roam-ai .venv/bin/python scripts/parity_run.py --doc F1,F3,F5 --effort high --out "$HIGH"
.venv/bin/python scripts/parity_compare.py --out "$HIGH" --baseline-run "$MEDIUM"
.venv/bin/python scripts/gate_recheck.py --worksheet "$MEDIUM/adjudication.csv" --run "$HIGH" --out "$HIGH"
```

- `parity_compare.py --baseline-run` adds a section to `parity_report.md`: tokens, time to first token, model time, cost and share of `max_tokens` for each document in both runs, side by side, and every `conflict` or `dropped` on a gate field (pump_config or a trap field) that the baseline run did not have. A worksheet that already carries verdicts is never overwritten; a regenerated one goes to `adjudication.regenerated.csv`.
- `gate_recheck.py` (`--run`, alias `--high-run`; `--families`, default `F1,F3,F5,F7`) selects the chosen families' worksheet rows on pump_config or a trap field judged `old right` or `both wrong`, looks up the same row key and field in the high run, and writes `gate_recheck.csv`: the worksheet columns plus `high_value` and `status` (`matches_old`, `matches_medium`, `other`, `absent`; a `both wrong` row whose value returns to the old one is `needs_review`). The status compares the whole `high_value` (every distinct value found, joined) with the old and medium values under the comparator's `format` rule, so several values never match one; a non-empty `high_value` is never `absent`. The worksheet is only read. Cells a spreadsheet left untouched are read as UTF-8 and cells typed into it in `--encoding` (default `mac_roman`).

Every artifact is compared as a multiset of rows, each row as canonical JSON; the Parquet grains are first put under the reference schema with a safe cast. It then compares production mode with corpus mode byte for byte, stages every `<run set>/<document>/report.md` under `--runs` in production mode (well: the corpus match for the same source document), and checks that every F1 pump section resolves to a canonical model. Outputs hold client data and must go outside this folder; `hashes.txt` lets two runs be compared.

## Running a document: the run store and its record

```bash
export ESP_RUN_STORE_DIR="<run store dir>"          # outside this folder: runs hold client data
export ESP_EXTRACTION_ASSETS_DIR="<extraction asset dir>"
AWS_PROFILE=roam-ai .venv/bin/python -m extraction --pdf <pdf> --org <id> --well <id>     # full chain, one Bedrock call
.venv/bin/python -m extraction --report <report.md> [--pdf <pdf>] --org <id> --no-well     # no model call
```

`--pdf` alone runs Detect, Prep, Extract (after checking the credentials are the datascience account's), Validate and stage, Store and Record. `--report` reuses a report and calls no model; with `--pdf` as well, Detect and Prep run and grounding is evaluated, and without it the checks that need them are not evaluated and the notices say so. `--well <id>` or `--no-well` (an unmatched well: no load rows, no key minted) is required. Options: `--budget-s` (default 900), `--model-id`, `--effort`, `--max-tokens` (default 128000), `--no-clarifications`, `--run-id <id>` (use this id, in the tool's own format; refused if `runs/<id>/` exists) and `--source-name <name>` (with `--pdf`: the file name prep records and the prompt names, in place of the PDF path's basename). The tool prints one line, starting with the `run_id`; it exits 0 when the run succeeded, 1 when it failed (its `run.json` says why) and 2 when it could not start.

A run lives in `$ESP_RUN_STORE_DIR/runs/<run_id>/`, where `run_id` is `YYYYMMDDTHHMMSSZ-<8 hex>` (the UTC start second, then random hex: sortable and unique). It holds `run.json`, `source.json` (path and SHA-256 of the PDF and of the report), `report.md`, `prep_manifest.csv`, the three grains as Parquet (`pump_config`, `esp_well_design_context`, `curve_observations`), `quarantine.jsonl`, `findings.jsonl`, `unknown_models.jsonl`, `review.jsonl`, `notices.jsonl`, `d16_log.jsonl`, `d17_log.jsonl` and `gas_log.jsonl`; and, when the run staged rows for a well and is not an empty extraction, `well_entry.json` (`extraction/well_entry.py`): the well's proposed `pump_parameters` and `wellbore_parameters` maps, each value an envelope `{value, unit, source: design_document, note}` as the product's validator (#1218) accepts it, and a review part with each value's starting status (`settled`, `to check` or `blocks publish`), its reasons, printed text and page, and the pump string's sections, checks and status. It holds no filesystem path. Every file is written to a temporary name and renamed into place, and each is written as soon as it exists, so a failed run keeps what it produced. The Lambda writes the same layout to S3, under `runs/<run_id>/` (`cdk/README.md`).

`run.json` is written first with `status: running` and a `deadline_at` (start plus the budget), and last with `succeeded` or `failed`. A reader (`extraction.run.read_record`) treats a `running` record past its deadline as failed and marks it `stale`. Fields:

- `run_id`, `status`, `started_at`, `deadline_at`, `ended_at`, `budget_s`, `mode` (`pdf` or `report`)
- `organization_id`, `well_id`, `family` (`generic` on the generic route), `family_source` (`detect` or `report_frontmatter`)
- `route` (`template` or `generic`), `forced` and `forced_from` (`--force-generic`: the family Detect matched), `family_hint` and `missing_roles` (a family matched with required pages missing), `near_misses` (no family matched)
- `source` (`pdf` and `report`, each `path` and `sha256`, or null; `source_name`, the PDF's file name as uploaded: `--source-name`, else the PDF's basename, null without a PDF; `source.json` holds the same block); `pages` (`page_count`, `kept_pages`, and each page's Detect roles)
- `staged` (the report's rows per grain table, before the load) and `rows` per grain (loaded; none without a well); `quarantine` (count); `findings` (`total`, `by_round1_severity`, `by_spec_severity`; `none` for guards); `spec_validation_status`; `blocks_publish`; `review` (`items`, `needs_review`, `informational`); `unknown_models`
- `error` (`code`, `message`, `details`, `stage`) or null. `status` is the run's own outcome; the document's validation verdict is `spec_validation_status`
- `model` (`model_id`, `effort`, `max_tokens`, `clarifications`, `prompt_bytes`, `stop_reason`, `model_time_s`, `time_to_first_token_s`) and `tokens` (`input`, `output`) and `cost_usd` (from `extraction/compare/pricing.json`), all null without a model call
- `hashes`: `report_sha256`, `prompt_sha256`, `contract` (the prompt's asset hashes), `clarifications`, `stage_assets` (seed, evidence, catalogue)
- `stages_s` (each stage's duration: detect, prep, assemble, extract, stage, store, record) and `store` (`files` written, `failed_at`)

Failure codes are the extraction codes plus `REPORT_INVALID` (the report and its structure findings are stored), `LOAD_HALTED` (D17-HALT: grains, findings and review are stored; the load is halted) and `STORE_FAILED` (`store.failed_at` and `error.details.failed_at` name the file the run could not write). If even the last `run.json` cannot be written, the `running` record stays and reads as stale once its deadline passes.

## Confirming an entry

An engineer confirms a run's `well_entry.json`; the confirmed values become one row of an append-only table. Nothing is overwritten or deleted: a well's current entry is its latest confirmed row per environment, organisation and well.

```bash
export ESP_RUN_STORE_DIR="<run store dir>" ESP_EXTRACTION_ASSETS_DIR="<extraction asset dir>"     # local mode
.venv/bin/python -m extraction.confirm --run-id <id> --as-proposed --confirmed-by <name>
ESP_APP_MODE=s3 AWS_PROFILE=roam-ai .venv/bin/python -m extraction.confirm --run-id <id> --as-proposed   # S3 mode
```

- **The CLI** (`extraction/confirm.py`) reads the run's `run.json` and `well_entry.json`, builds the request, writes it create-only to `confirmations/<confirmation_id>/request.json`, and prints its result. Each value goes as proposed unless an option changes it: `--as-proposed` settles every value to check; `--set KEY=VALUE` (repeatable) corrects a top-level key, marked manually corrected with source `design_document` (`vapor_pressure_psia`: `ops_entered`); `--accept-anyway REASON` accepts, uncorrected, what blocks publish and a pump string whose order check fails; `--leave-to-check KEY` leaves a value to check, so that the writer refuses (tests). `--environment` is `prd` (default) or `dev`; `--confirmed-by` defaults, in S3 mode, to the STS caller's session name; `--wait` (default 180 s) bounds the wait. In S3 mode (`ESP_APP_MODE=s3`) the writer Lambda answers and the result is polled; beyond the viewer's permissions this needs `s3:PutObject` on `confirmations/*`, and `s3:ListBucket` (prefix `confirmations/`) with `s3:GetObject` there to read the result ("Run the app against S3" lists them all). In local mode the writer runs in the process, against the store `ESP_RUN_STORE_DIR` names, in the same layout: the run's PDF must be at `intake/<run_id>.pdf` (the viewer's upload form writes it there, with its labels, beside its copy named by SHA-256), and `--confirmed-by` is required. Exit status: 0 written, 1 refused, failed, stale or no result in time, 2 nothing sent.
- **The contracts** (`extraction/confirmation.py`, standard library only) hold the layout, the request, result and row shapes, and the two storage backends (`LocalObjects` keeps an object's metadata, when it has any, in `.<name>.metadata.json` beside it, where tests and replays write it). Every key is under `s3://roam-ds-assets/esp-design-extraction/`, and none is built from an organisation or a well id: `confirmations/<id>/request.json` and `result.json`; `design-records/<document_sha256>/document.pdf` and `versions/<id>.json`; `well-entries/environment=<env>/<id>.json`.
- **The writer** (`extraction/confirm_writer.py`; on Lambda `esp-design-extraction-writer`, command `lambda_function.confirm_handler`, in the same image) creates the result `running`, create-only (a 412 or 409 is a duplicate event, and it stops), checks the request, and on a refusal writes only the result. Otherwise it writes the document (create-only; already there is fine), the version, the row (create-only: the commit point), then the result. Its checks: the request keeps the contract and its key's id; `run.json`, `well_entry.json` (for `manual`, none: "Entering a run by hand") and `intake/<run_id>.pdf` are there and agree with the request's organisation, well and document SHA-256; when `intake/<run_id>.pdf` carries a valid `environment` label (an upload in the product: "Run the viewer"), the request's environment is it, else the refusal `environment is '<the request's>'; the upload's is '<the label's>'` (the label is read with a HeadObject, `S3Objects.head` and `LocalObjects.head`, a 403 or 404 reading as no label; a run without one is checked as before); the entry method is `extracted`, `transcription` or `manual` (a run entered by hand: "Entering a run by hand", below) and the environment `dev` or `prd`; every value of the entry is given once, none is left to check, any changed value is marked manually corrected, and what blocks publish is corrected so that its check passes or accepted anyway; the string's checks that read only its sections (sections, V-08, V-09, models, complete) run again on the final sections, a failed order check needing an accept-anyway reason and any other failure a settled or corrected string; the final string value is its sections; `design_document_ref` is left to the writer; both maps pass #1218's rules (`well_entry.parameter_problems`, the product validator restated); the row fits the table's types; and every pump model is a catalogue spelling, against the catalogue snapshot after its hash check. The version's `labels` gain `origin`, `uploaded_by` and `pushed_from` when the upload carries them; the request and the row are as before. The run log gets one `PIPELINE_EXECUTION` row per request, as a run's: written `RUNNING`, updated to `SUCCEEDED` (written) or `FAILED` (refused or failed). On Lambda the writer cannot list, so S3 answers 403 for a key that is not there: a 403 on the request, on `runs/<run_id>/…` or on `intake/<run_id>.pdf` reads as not there, and the refusal names the key and says so; a 403 on `assets/` is a failure. The readers take only a 404 for not there.

Rows and versions are read once and kept. The app's review reads them.
- **The app** (`app/main.py` draws, `app/review.py` decides) opens a run that stored a `well_entry.json` in **Review & confirm** until a version of that run has its row; then it shows what was written, read only. A run that ended and stored none offers **Enter by hand** ("Entering a run by hand", below). The run's files are under **Run details (technical)**, drawn with `ESP_SHOW_TECHNICAL=1` ("Run the viewer"): the pipeline's own files as it stored them, where the read-only `review.jsonl` list is now **Signals**. The PDF is beside the review, half the width, and every page chip turns it. The header names the organisation and well exactly (each character that would not show marked by its sign, as the upload form marks it, with the same line on the signs shown, and not in emphasis, which an edge space breaks; the Write pop-up names them the same way), where the entry goes (the upload's `environment` label when it carries a valid one, the form's or the product's: Test wells for `dev`, Live wells for `prd`, the upload form's words; without one, Test wells for `lab-check` and Live wells for every other organisation; a run started by an upload in the product says so in the header; `review.write` refuses `lab-check` anywhere but Test wells), the kind of report (a known vendor's, or not a known vendor report), the printed design date and who confirms. The values come in groups: the string; **Found** (to check, with a value); **Not found** (to check, empty); and, collapsed, **Settled or corrected** (by an engineer, here or in an earlier confirmation) and **Kept as read, not checked** (settled by the extraction: no one checked them, and no screen shows them as settled). Each value can be settled; corrected (a value, the unit #1218 allows for its key, source the design document or outside it, `design_document` or `ops_entered`, a note); settled as empty; or, if it blocks publish, accepted anyway with a written reason. The string is settled as proposed, accepted anyway, or edited (below). **Check group by group** opens up to four pop-ups in turn (string, found, not found, Write), each with its own page viewer; ticked values are settled together, unticked ones are left out of the group check (the record's `pulled out`: still to check, marked on the review), and a value that blocks publish cannot be ticked. **Write** is on only when `confirm_writer.check` accepts the request as it stands and the run may write where the entry goes (`review.environment_problem`: `lab-check` to Test wells only), and otherwise says why. It puts `request.json` and polls the result for up to 180 s, as the CLI does; a result that reads as stale while the row `well-entries/environment=<env>/<confirmation_id>.json` is there reads "written; its result wasn't updated". When the document already has a confirmed version for the well in the same environment (`latest_version` within it: a version written to Test wells never comes back in Live wells, nor the other way), every correction comes back (shown beside the new reading when the proposal moved), and a settlement or accept-anyway reason comes back where the proposal is unchanged. If the run's printed design date (`confirm_writer.printed_design_date`) is older than that of the well's current entry in the target environment, the header and the Write pop-up warn and show both dates; when either is undated they say "can't compare". Decisions not yet written live in the browser session only.
  - **The pump string.** Its block, the String pop-up and the editor show the string's checks that read only its sections (`well_entry.final_string_checks`: sections, order, stages against housings, models, complete) on the sections as they stand, from the moment the review opens, and beside them, marked as about the document as read, those that read the report (scenarios, conflicts, the sections' review flags, the head sum) as the entry has them (`review.string_checks`, `document_checks`). A string that would start settled starts to check, with the check's reason, where one of the first group fails on its proposed sections though it passed when the entry was built (`review.starting`). Where the string as read writes no pump string (a model not found, an order or stage count missing), settling it as proposed stays allowed, and the block and the pop-up say so and that Edit sections can fix it. **Edit sections**, in the block or in the String pop-up (there it first pulls the string out of that batch, then closes the pop-up), opens the editor in place beside the PDF, on any string not yet written: a copy, one row per section, whose order numbers follow the rows, 1 the deepest (where the proposal had none, the screen says the order shown is unchecked). A section can be added at a chosen place, removed, moved up or down, and edited: its model, a searchable pick from the catalogue snapshot's names (its model or the lookup's candidates first; a name without a head curve is shown as such), or instead marked **not in the catalogue** with every name the document prints for it (free text, pre-filled from the extraction); stages and housings, whole numbers of at least 1, or empty (every number can be cleared); stages per housing as text (a comma list of whole numbers lets V-09 run); role (primary, taper, gas handler or none); top and bottom MD in ft. The checks re-run after every change. **Save** applies the copy, **Cancel** drops it, **Back to the string as read** resets it to the proposal; Save is off while a section has neither a catalogue model nor the mark, and while a save that would write no pump string (a section marked not in the catalogue, or one with no stage count) has no written reason; the step records the reason, and the screen's "Recorded, not written" shows it. Write is off while the editor holds unsaved changes. A save makes the string manually corrected when its sections differ from the proposal, its final the sections' value as `confirm.corrections` builds it when every section has a catalogue model and a stage count, else null (`review.not_written`): the string is then recorded in the version and not written to the row. A failing order check after a save blocks publish: correct it, or accept it anyway, which keeps the edits. The request's sections hold exactly `SECTION_FIELDS`; the page, the printed name and the mark stay in the app (the marks and the reason are in the save's history step).
  - **Plain words.** The engineer's screens (the review mode, the pop-ups, the Write pop-up and the confirmed view, with every message on them) carry no identifier or code: no rule or check id, key, section position, family code, run or confirmation id, object key or hash, and no internal word (staging, route, alias list and the like). Live wells and Test wells, the upload form's words, stand for `prd` and `dev`; sections are counted 1 to N, 1 the deepest; keys go by their #1218 labels; a document goes by its file name and dates, a confirmation by who made it and when. Each reason, note and refusal says what was noticed and what to check (`review.in_words`, `note_words`, `refusal_words`). The record keeps the raw form, and so does Run details. `tests/test_screens.py` scans every message the app makes, and with `pytest -m store tests/test_screens.py` every engineer screen of every run in `ESP_RUN_STORE_DIR`, for the id patterns it lists; what a scan leaves out is listed there. With the technical views off, `tests/test_hosted.py` scans every page whole, for those patterns and for the names of AWS and its services, of settings, and commands. Where a label and the record differ, the label is the engineer's: the Write pop-up's rows (a row with none is left out) and the badges say *left out of a group check*, *kept from an earlier confirmation* and *needed no check: kept as read* (the badge: *kept as read*) for the record's `pulled out`, `carried from …` and the values the extraction settled; a run still recorded as running past its deadline reads *stopped without finishing* (Run details and the technical table keep `failed (stale)`); the watch page shows the elapsed time, and its limit only with the technical views. Who confirms or confirmed is drawn as text (`st.text`), exactly as recorded and never through Markdown, which would make an address a link; with no one to confirm as it reads *no one signed in*.
  - S3 mode confirms as the STS caller's session name (`extraction.confirm.caller`, read once per session), or, behind a sign-in, as the signed-in user (`ESP_SIGNED_IN_USER_HEADER`: "Run the app against S3"); with neither, Write is off and says so, and with the two role settings set and no header named it is off in either mode. On the run list, the upload page, the watch page and an engineer's screen the sidebar says only when the runs were read, with **Refresh**; the bucket and prefixes show under Run details (with `ESP_SHOW_TECHNICAL=1`). The check before Write needs the catalogue snapshot, `ESP_EXTRACTION_ASSETS_DIR`, as the writer does; S3 mode fetches it when that is unset ("Run the app against S3"). Local mode reviews and does not write, unless `ESP_CONFIRM_OFFLINE_AS=<name>` is set: then it writes into the local store as that name, with `confirm_writer.confirm` called in the process, as the CLI's local mode does (the run's PDF at `intake/<run_id>.pdf`, which the form writes with its labels; the store outside this folder). That is for tests and screenshots.
  - **The record.** Each value's `history` in the request (and in the version) is a list of `{status, by, at, reason}`, `by` the confirmer for every step a confirmation adds, `at` its UTC time in `confirmed_at`'s format:

    | Step | `status` | `reason` |
    |---|---|---|
    | the proposal (first, as the CLI writes it) | the entry's starting status (for the string, `review.starting`'s) | its reasons joined by `; `, or null; `by` is `extraction`, `at` the run's `ended_at` |
    | settled in a batch | `settled` | `batch <n> · <group> · "<sentence>"` |
    | pulled out of a batch | `to check` | `batch <n> · <group> · pulled out` |
    | one by one (settle, correct, settle as empty, accept anyway) | the status reached | null; an accept-anyway reason is the item's `accept_anyway` |
    | one by one on a transcription (settle, settle as empty) | the status reached | `checked against the original scan` (`review.CHECKED`); a correction and an accept anyway stay null |
    | the string's sections saved in the editor, one step per save | `manually corrected` (a save that brings the sections back to the proposal: the string's starting status; one that changes only the marks: its status) | `edited · added <n> · removed <n> · moved <n> · changed <field>, <field>`, then, for a string not written, ` · not in the catalogue: "<printed>", "<printed>"` when a section is marked, and ` · not written: "<reason>"` always |
    | carried on a re-run | the carried status | `carried from <confirmation_id>`, after the earlier version's steps, which keep their own `by` and `at` |

    `<n>` numbers the confirmation's batches from 1, `<group>` is `string`, `found` or `not found`, and `<sentence>` is the pop-up's button, verbatim, e.g. `These 3 values match the document as printed, with bare-psi pressures taken as absolute.` A string accepted anyway in its pop-up is settled with the sentence `Accept the string anyway` and its reason in `accept_anyway` (an edited string stays manually corrected, its edits kept). A batch reason parses with `batch (\d+) · (string|found|not found) · (?:"(.*)"|pulled out)` (`review.BATCH`).

    **The edited step.** Each part shows only when it is not zero, in that order, joined by ` · `; with none, the reason is `edited` and what follows. The counts are against the string before that save, its sections matched by identity, not by content: *added*, the sections new to it; *removed*, its sections gone; *moved*, the fewest of the sections kept that have to move to give their new order (those kept, less the longest run of them still in their old order: one section moved three places is 1, two swapped are 1); *changed*, the contract's names of the fields, other than the order, that differ on a kept section, in `SECTION_FIELDS` order, and `section_order` when a kept section's order number was not its place before the save (missing or wrong: a save numbers the sections by row). A move or an addition renumbers the sections around it without counting as a change. Each `<printed>` and the `<reason>` are JSON strings, so a quote in them is escaped. Opening the editor from the String pop-up adds that batch's pull-out step first; an accept-anyway reason goes in `accept_anyway`. An edited reason parses with `review.EDITED`: `edited(?: · added (\d+))?(?: · removed (\d+))?(?: · moved (\d+))?(?: · changed ([a-z_]+(?:, [a-z_]+)*))?(?:(?: · not in the catalogue: (<q>(?:, <q>)*))? · not written: (<q>))?`, `<q>` a JSON string, `"(?:[^"\\]|\\.)*"` (`review.QUOTED`). Every save that writes no pump string carries ` · not written: "<reason>"`, and ` · not in the catalogue: …` comes before it only when a section is marked. A carried string's marks and reason come back from its latest edited step. Tests: `tests/test_review.py`, `tests/test_editor.py`.
- **Tests:** `tests/test_confirm.py`. With `ESP_WELL_ENTRIES_STORE` (a store holding confirmed rows) every row is checked against the schema, and with `ESP_MONOREPO_DIR` (the monorepo clone) the map rules are checked against #1218's own validator, read with `git show 6831cbd6:…`, on those rows and on negative cases.

## The generic route

Detect decides the route (`extraction.detect.route`, which wraps `detect` unchanged):

| Detect finds | Route | Recorded |
|---|---|---|
| a family, with all its required pages | `template`: the family's contract, unchanged | `route = template` |
| a family, with required pages missing | `generic` (`REQUIRED_PAGES_MISSING` no longer ends the run) | `family_hint`, `missing_roles` |
| no family, and a text layer | `generic` | `near_misses`, `family_hint = null` |
| `IMAGE_ONLY`, `AMBIGUOUS_TEMPLATE`, `PREP_FAILED` | none: the run fails, as before (a scan: "The transcription route") | `error` |

On the generic route, `prep_generic` keeps every page whose text reaches the 20-character floor and drops the rest (manifest role `unmapped`). The prompt is `generic-pass-a.md` and `generic-contract.md` in the family frame (report contract, both schema blocks, and every family's proposed fields as `family` and `field_as_printed`), with one line of route context naming the family hint and its missing pages. A prompt over 322,766 bytes, the largest parity prompt, fails `GENERIC_TOO_LARGE` before any model call. Staging expects `vendor_family: generic`; D31 resolves a model only by an exact match (case and outer spaces aside) to a canonical name, from the catalogue or the seed, or to a seed alias that every family maps to one canonical, so anything else is an unknown model. Only the validator's general rules run, never `V-F*`. Every review item carries `generic_path` and needs review, `spec_validation_status` is at least `needs_review`, and a notice reads "Extracted without a vendor template: every value is unverified." `--force-generic` sends a template document down the generic route, with no hint, for the yardstick; the record shows `forced` and `forced_from`.

`tools/yardstick.py --template <store or run> --generic <store or run>` pairs each generic run with the template run of the same PDF (by SHA-256), or compares two run directories as given, and pairs their `stg_pump_config` and `stg_design_context` rows as `extraction/compare` does. Per document it prints the row alignment (rows per table on each side, template rows matched, the cases each side covers), agreement on matched rows only, every dropped or conflicting template value by cause (`grain`: rows that do not line up; `scenario`: a case one side lacks; `vocabulary`: a field the generic contract decides differently, a value under another key, or one not repeated per case; `genuine`: printed, in scope, and left out or wrong), and the genuine misses by field. `--fields` adds per-field counts and `--diff` every differing value. The command-line summary prints the report's staged rows beside the loaded ones (`staged 2/1/14 · load 0/0/0`), so a run without a well does not read as empty.

## The transcription route

A scanned design document has no text layer, so its run fails `IMAGE_ONLY` at Detect, before any model call; the run's page then says, in plain words, to transcribe the scan with the skill and upload the transcription. The skill is `skills/transcribe-design-scan/`: `SKILL.md` (the method, written for Claude Opus 5.5 reading the page images; no OCR engine), `reading-aids.md` (drawings, charts, tables, sideways vendor tables), `scripts/render_pages.py` (the scan's SHA-256 and page count, every page as a PNG at 200 dpi, a crop of a region at a higher resolution), `scripts/build_transcription.py` (the transcription) and `fonts/` (DejaVu Sans Mono and its licence). It is used, on claude.ai or in Claude Code, as a zip with the folder at its root, built outside this tree:

```bash
(cd skills && zip -r -X "<out dir>/transcribe-design-scan.zip" transcribe-design-scan)
```

`fonts/LICENSE` is the font's licence, verbatim, as its terms require.

The scripts need pypdf, reportlab and a renderer (pypdfium2 with Pillow, or pdftoppm), and install packages only in claude.ai's sandbox (where `/mnt/user-data/` exists): there each installs what it misses with pip, with `--break-system-packages` only when plain pip refuses. Anywhere else, Claude Code on an engineer's Mac among them, they install nothing: the method has Claude make a virtual environment in the working folder (`python3 -m venv .venv`, then `.venv/bin/pip install pypdf reportlab pypdfium2 pillow`) and run both scripts with its Python, never the machine's own. Outside the sandbox, a script that misses a package names it, prints those two commands and stops with exit code 4.

The transcription is one PDF, `<scan name without .pdf> - transcription.pdf`, written to `/mnt/user-data/outputs/` when that folder exists, else beside the scan:

- one typed page per scan page, in order, each starting with the line `Transcription - page N of M - check every value against the original scan attached to this file.`, then a blank line, then the page as typed (the page files `page-001.txt`, … hold only the page's content). The pages are DejaVu Sans Mono 12 pt on pdfplumber's layout grid, 7.25 pt columns and 13 pt lines (`DEFAULT_X_DENSITY` and `DEFAULT_Y_DENSITY` in 0.11.9), each grown from Letter to fit its longest line and its line count with a margin of 5 columns and 3 lines, so no line wraps, each scan page stays one page, and Detect and Prep read every typed line back with its columns, 5 columns in. The run then goes as any PDF with a text layer does;
- the scan, attached byte for byte under its own file name (`original-scan.pdf` when that name cannot name a PDF);
- the mark, the document-information entry `/RoamTranscription`, one JSON object: `schema` 1, `skill` `transcribe-design-scan`, `skill_version` `"1"`, `original` (`name`, `sha256`, `pages`, `bytes`), `attachment` (the attached file's name), `transcribed_at` (UTC, ISO 8601), `model` (as the transcriber names itself, given to the build script) and `unsure` (one `{page, line}` per `[?]`, the line counted in its page file).

The build script refuses on any gap (a page file missing or empty, or a count of page files that is not the scan's) and writes nothing then. Tests: `tests/test_transcription_skill.py`.

**Recognition** (`app/transcription.py`, from the PDF's bytes alone, kept by their SHA-256): a transcription when the mark parses with schema 1, exactly one attachment has the mark's SHA-256, and that attachment's page count is the mark's and the transcription's; a broken transcription when the mark is there and anything else is not so, with the reason in plain words; otherwise an ordinary PDF. The upload form says a transcription is one, with the original's name and page count, and that the original scan is inside the file; it refuses a broken one, with its reason, asking for the file exactly as the skill made it.

**Review** of a run whose source PDF is a transcription (`tests/test_transcription.py`):

- the header's report reads "typed from a scan", and a warning says that the document is a transcription typed by Claude from the scan's page images, that every value must be checked against the original scan beside the review, and which pages have readings marked unsure;
- the PDF pane and every pop-up's viewer open on the original scan, with a switch to the transcription; a page chip turns whichever is showing, page N being page N in both. The document goes by the original's file name, unless that name is an id (`review.document_name`);
- the batch sentences name the original scan: `These N values match the original scan as printed` (the judgement clauses unchanged), `I looked through the original scan: these N values are not printed.` and `The string matches the original scan.`;
- a value settled one by one, or settled as empty, records `checked against the original scan` as its step's reason (the record's table above);
- the request goes as `entry_method` `transcription`, set by the app after the CLI's builder, which `extraction/confirm.py` keeps; the writer takes it;
- on the template route the review starts as a generic run does (`review.from_scan`): every value from the document, every section and the string gain the reason `typed_from_scan`, shown as "Typed from a scan: check it against the original.", and start to check unless they block publish; `design_document_ref` and `vapor_pressure_psia` stay as they are. The stored entry is not changed: the review's proposal step records that start, and the version's `starting_status` stays the stored entry's. On the generic route nothing changes;
- a run whose source is a broken transcription opens with a warning, and Write stays off, saying why.

An ordinary run is reviewed as before. A run whose PDF the app cannot read cannot be told for a transcription: its pane says the pages cannot be shown, and its request goes as `extracted`.

## Entering a run by hand

A run that stored no `well_entry.json` (a scan that failed `IMAGE_ONLY`, a model timeout, an unreadable PDF, …) has nothing to review, and can be entered by hand instead (`tests/test_manual.py`).

- **The empty proposal** (`well_entry.empty_entry(organization_id, well_id)`) is the entry an extraction would store had it read nothing, in `build_entry`'s shape: every key of the field list in order, `to check` with the reason `entered_by_hand` ("Entered by hand: nothing was read. …"), except `vapor_pressure_psia` and `design_document_ref`, settled and empty with their notes as always; both maps empty; the pump string empty, `to check`, with no check run on it. Its `review.route` is `manual`, which marks it: `review.from_scan` acts on the template route only, so a transcription entered by hand is not re-marked as typed from a scan. Nothing stores it: the app and the writer each build it for the run.
- **The offer.** A run's page offers **Enter by hand** when the run has ended (failed or succeeded, or running past its `deadline_at`, as the run list reads stale), stored no entry, names its organisation, well and document SHA-256, and its PDF is in the store (`review.by_hand`): beside the scan's message for `IMAGE_ONLY`, otherwise with a plain line, which adds, for `MODEL_TIMEOUT` and `MODEL_ERROR`, that uploading the document again retries the extraction (`review.failure_words`). With `ESP_SHOW_TECHNICAL=1` the page stays the run's technical page; without it the page is the watch page's plain words ("Run the viewer"). Enter by hand opens the engineer's screens either way. Watching a run that failed ends on the same offer, under the same conditions, and its **Enter by hand** opens the run's page in that flow; without the offer the watch page says what happened in plain words (`review.failed_words`).
- **The review** is the review mode over the empty proposal, beside the PDF: the header says nothing was read and every value is typed from the document; the report reads "entered by hand" and there is no design date. Each value is corrected (the three pressure keys' Value help says the value is absolute: add 14.7 to a gauge reading and note the printed value) or settled as empty; the string is built in the editor, or settled as empty; the batch pop-ups are as ever. Write stays off until something is typed, a value corrected to a value or a section in the string (`review.entered`, the writer's rule), and says so. A transcription keeps its warning and opens on its original scan. The request goes as `entry_method` `manual`, a transcription's too. A document and well already confirmed in the same environment come back through the carry-over, as for any run. Once written, the run opens on its confirmed view, which says it was entered by hand.
- **The writer**, for `manual` only: the run must have ended (the same stale rule), else `runs/<run_id>/run.json says '<status>': the run has not ended`; it must have stored no `well_entry.json`, else `runs/<run_id>/well_entry.json is there: this run has an extraction to review`, a 404 or a 403 on it reading as none on this path only (the writer cannot list); every other check runs unchanged against the empty proposal; something must be typed, else `nothing was entered: …`; no `report.md` is read, so `design_date` is null. The version is written as ever, the empty proposal as what was proposed. The extracted and transcription paths are unchanged.

## Run the viewer

`app/main.py` is a Streamlit viewer over the run store, in local mode (the default) a directory and in S3 mode the bucket the Lambda writes ("Run the app against S3"): every run, newest first and filterable, and each run in full (both statuses, the error, the source PDF page by page, the grains, curves, findings, signals list, notices, unknown models, logs, and the report as plain text). A run with a proposed well entry opens in review instead ("Confirming an entry"). Start it from this folder, so that `.streamlit/config.toml` applies:

```bash
export ESP_RUN_STORE_DIR="<run store dir>"
export ESP_SOURCE_PDF_DIRS="<pdf dir>[:<pdf dir>]"   # optional: folders searched for source PDFs
export ESP_SHOW_TECHNICAL=1                          # optional: the technical views; unset, they are hidden
export ESP_CONTACT="<whom to tell>"                  # optional: whom the pages say to tell when something goes wrong
PYTHONDONTWRITEBYTECODE=1 .venv/bin/streamlit run app/main.py
```

**Who it is for.** By default every page is an engineer's: it says what it is for and what to do next, and shows no run or confirmation id, hash, family or error code, field key, AWS or setting name, command, or the words dev and prd; organisations and wells show exactly as listed, and marked. The technical views are drawn only when the app is started with `ESP_SHOW_TECHNICAL=1`; unset, or with any other value, none of them is drawn (`app/hosted.py`: `technical`), and none is removed:

- **Run details (technical)**, with its tabs, on a run's page;
- the page of a run that stored nothing to review, `Run <id>` over those tabs: hidden, the run opens on the watch page's plain words instead (what happened, what to do next, and **Enter by hand** where the run offers it);
- **Run ids and codes (technical)** under the run list, and the list's **Cost** column;
- **Details (technical)** on the upload, watch and could-not-read screens, and the watch page's **Launch log (technical)** and **Run record (technical)**;
- the sidebar's line naming the bucket and prefixes (S3 mode);
- the set-up messages that name settings and commands (no run store named, an S3 variable missing, a mode that is neither, one of the two role settings without the other): hidden, one plain line, "This app is not set up yet";
- an uncaught error's traceback: the page says in plain words that the runs could not be read, and for an error outside the page's own handling (a button's callback) the app sets Streamlit's `client.showErrorDetails` to `none` (`full` with the switch on), so its one line says nothing of the error.

What a page leaves out goes to the app's log instead: one logger, `esp_design_extraction.app`, to standard error, one line per occurrence with the error's class and message (`hosted.hidden`; an uncaught error with its traceback; Streamlit logs its own for a callback's). A rerun of the page is not another occurrence. `ESP_CONTACT` names whom a page says to tell or ask when something goes wrong, written to follow "tell", as `the ESP data team (esp-data@example.com)`; unset, the pages say "whoever looks after this app". The upload page says a run takes 3 to 8 minutes; its tick before **Start the run** is the engineer's own check: *I've checked the organisation, the well and the document*.

**Fonts.** Barlow (400, 500, 600), Barlow Semi Condensed (500, 600) and IBM Plex Mono (400, 500) are bundled under `app/static/fonts/`, verbatim from the google/fonts repository on GitHub, each family beside its licence, `OFL.txt`; `MANIFEST.txt` there gives each file's source URL and SHA-256. `.streamlit/config.toml` serves them (`server.enableStaticServing`, and one `[[theme.fontFaces]]` per file, its `url` relative, so it follows `--server.baseUrlPath`) and names no outside address: a page asks nothing of any server but the app's own. Streamlit serves `static/` from beside the script it is started on, so start `app/main.py` itself.

**New run from a PDF** starts a run from the viewer. Its wells are the product's live well lists, read from Athena in the datascience account (`app/wells.py`): a switch, **Live wells** (production: the data source `roam_prd_ddb`) or **Test wells** (test: `roam_dev_ddb`), starts on Live wells, then on the side last chosen in the browser session, and each list is one query, `SELECT organization_id, well_id FROM "<source>"."default"."esp_well_configuration_v2"`, started, polled and read a page at a time through boto3's Athena client in `us-east-1`. Two settings: `ESP_ATHENA_OUTPUT_LOCATION`, the query results location (default `s3://aws-athena-query-results-640168431387-us-east-1/`, the location the Athena console uses in this account), and `ESP_ATHENA_WORKGROUP` (default `primary`). Each list is read once per app process and kept until **Refresh** beside it; the form says when it was read, how many wells it holds and how many rows it left out (an empty `organization_id` or `well_id`). Every value is kept exactly as returned (no strip, no case-folding, no collapsing); exact duplicate pairs are dropped. Every name shows each character that would not show as its sign (`wells.marked`, one sign per character): ␣ a plain space at an edge or in a run of two or more, ° a no-break space, → a tab, ▫ any other space character, ¦ a character with no width (a control character, or one of Unicode's default-ignorable characters: zero-width spaces and joiners, direction marks, the soft hyphen and the like). One line says in plain words what the signs shown mean (`wells.key`) and, where two organisations or two wells of one organisation differ only by case or by such characters (`wells.near`), that the product keeps them apart: the exact one is to be chosen. No two names of one list show alike, here or in the run list's filters (`wells.labels`), so a choice, which Streamlit maps back by its shown text, maps back to exactly its name: where two names still mark alike (two kinds of space behind ▫, or a sign written in a name), each is followed by the characters behind its signs, in words, as `Org▫Alpha (en space)`. The upload's labels take printable values only (`extraction/intake.py`, Python's `str.isprintable`), so a name with °, → or ▫, or with ¦ for a format or control character (a zero-width space or joiner, a direction mark, a soft hyphen), starts no run: as soon as it is chosen, the form says no run can start for it yet, and Start stays off (`app.intake.refused`, the labels' own rule, `decode_label`, imported from `extraction/intake.py`). The PDF's file name, the label `source-name`, is checked the same way once the file is added: a name the labels refuse is said in plain words (rename the file and add it again), and Start stays off. Variation selectors and fillers, also shown ¦, are printable and pass. Test wells add the lab's own organisation, `lab-check`, with the well's name typed, sent exactly as typed (a name of spaces alone is no name); Live wells never offer it. A list that cannot be read keeps the form off, says so plainly with **Retry**, and puts the error under the page's technical section (hidden, in the log); nothing falls back to a CSV (`ESP_WELL_LIST_PATH` names the snapshot only the tools read: `tools/detect_survey.py`, `tools/check_client_names.py`). The upload carries its list's environment, `prd` or `dev`, as the optional label `environment` (`app.intake.labels`), so the run writes there, its confirmation too: the writer refuses another ("Confirming an entry"). In local mode the form also needs the variables a run needs (`ESP_EXTRACTION_ASSETS_DIR`, and AWS credentials for the datascience account): it copies the PDF to `intake/<sha256>.pdf` in the store, and to `intake/<run_id>.pdf` with its labels beside it (`.<run_id>.pdf.metadata.json`, as `LocalObjects` keeps an object's metadata), which the store's `intake_labels` and the writer read as S3 mode's; it launches `python -m extraction --pdf … --run-id … --source-name …` as a detached process with its output in `launch/<run_id>.log`, and follows the run until its record is final. Apart from the well lists, the app makes no AWS call itself in local mode. In S3 mode the form puts the PDF at `intake/<run_id>.pdf` with its four labels and `environment` (`extraction/intake.py`'s encoding) and follows the run the same way; the upload starts the Lambda. The run list, the upload page and the watch page name a run by its organisation, well, document name, start and status in plain words (the run list and the watch page mark each name as the form and the review do, with the same line on the signs shown; the list's filters offer each name once, never two alike); run ids, stages, error codes, family codes and the like are under each page's technical section, drawn with `ESP_SHOW_TECHNICAL=1` (`tests/test_intake.py` scans them; `tests/test_hosted.py`, the pages with the switch off). An upload with no record yet is *waiting to start*; *not picked up* after 5 minutes with no run running (a `FAILED` row for its run id in the run log, `esp_design_extraction_logging`, and the function's CloudWatch logs say why); *expired* after 6 hours, Lambda's default limit for a waiting event.

**Started by an upload in the product.** The second way in needs no form. Where its push is deployed (`RUNBOOK.md` says where), the ESP product pushes a design PDF an engineer uploads there into this stack's bucket `esp-design-extraction-product-uploads-640168431387` (versioned; the product's dev account may put only under `dev/`, its prd account only under `prd/`; `cdk/README.md`), at `dev/` or `prd/` followed by the product's own key, so `<dev|prd>/<organization_id>/well-documents/<well_id>/esp_design/<file>.pdf`, with the metadata `uploaded-by` and `original-filename`; a push that fails leaves the product's upload in place, and nothing reaches this stack. Each `.pdf` created there starts the starter, `esp-design-extraction-product-intake` (`lambda_function.product_upload_handler`, the same image), which starts one run as the form does: it reads the event's version of the object, with its metadata, and puts it at `intake/<run_id>.pdf` with its labels, create-only, and that upload starts the extraction.

- The run id is the event's second, in the run id's format, then the first 8 hex digits of the SHA-256 of `<bucket>/<key>@<version id>` (the event's sequencer when it names no version). A repeated event is the same run: its put finds the upload there (a 412, or a 409 when another put races it) and is logged as a duplicate, with nothing else written. Each new version of the key is a new run.
- The four labels: organisation and well from the key, exactly as decoded (`unquote_plus`, as the extraction decodes its own); `sha256` of the bytes; `source-name` the push's `original-filename` when that decodes to a plain file name ending `.pdf` (in any case), else the key's file name.
- Four optional labels beside them (`extraction/intake.py`), percent-encoded UTF-8 like the four: `origin` (`product-upload`), `environment` (`dev` or `prd`, from the key), `uploaded-by` when the push carries it, and `pushed-from` (`s3://<bucket>/<key>?versionId=<id>`). `optional_labels` reads them, a missing or invalid one as absent; the form sets `environment` alone, and the extraction reads none.
- A key of another shape, an event that gives no run id, an object S3 refuses as not there (it answers 403 or 404, or `NoSuchKey`, `NoSuchVersion` or `AccessDenied`), or a label the four's rules refuse gets one `FAILED` row in the run log (`INTAKE_INVALID`, as a bad intake key's row is made; under the run id once there is one, else `ADHOC#<request id>`), and nothing is put. A read that fails otherwise (a 500, a throttle, a timeout: `INTERNAL_ERROR`, with the trace) and a put that fails otherwise (`STORE_FAILED`) each get a `FAILED` row and are raised, so that Lambda retries the event (twice): the same run, create-only. A run that starts writes no row of its own: the extraction's row is the run's. The event, which names the uploader and their IP, is never logged or stored.

In S3 mode the run list (**How it started**), the watch page and the review header say "Started automatically by an upload in the product"; who uploaded is not shown on any screen. Such a run writes to its upload's environment, as a form upload writes to its list's; a run without the label as before, and `lab-check` is still refused in Live wells: Write is off from the start, saying so. Local mode reads the labels the form keeps beside `intake/<run_id>.pdf`, and any kept there the same way.

In local mode the source PDF is found by its SHA-256 only: `intake/<sha256>.pdf` under the store root, then the PDFs under `ESP_SOURCE_PDF_DIRS`. The path recorded in `run.json` and `source.json` is shown as text and never opened. In S3 mode it is read from the location `source.json` records, only under the intake prefix, and only when its SHA-256 matches. Storage sits behind `app/store.py` (`RunStore`; `LocalRunStore` reads a directory, `S3RunStore` the bucket, its reads cached until **Refresh** in the sidebar). Tests: `tests/test_viewer.py` and `tests/test_intake.py`, and `tests/test_app_s3.py` for S3 mode on a fake bucket; `tests/test_hosted.py` for the switch, the plain pages, the hosted settings ("Run the app against S3"), the catalogue's fetch and the fonts; `pytest -m store` renders every run in `ESP_RUN_STORE_DIR`. Every suite but `tests/test_hosted.py` runs with the technical views on (`tests/conftest.py`). `tools/check_client_names.py <well list CSV> [changed files]` reports where the list's ids appear in this tree, by file and line only.

## Run the app against S3

```bash
export ESP_APP_MODE=s3                                   # local (the default) or s3
export ESP_BUCKET=roam-ds-assets                         # these three as the stack sets them for the Lambda
export ESP_INTAKE_PREFIX=esp-design-extraction/intake/
export ESP_RUNS_PREFIX=esp-design-extraction/runs/
export ESP_ATHENA_OUTPUT_LOCATION=s3://aws-athena-query-results-640168431387-us-east-1/   # optional, the default: the well lists'
export ESP_ATHENA_WORKGROUP=primary                      # query results and workgroup, as in local mode
export ESP_EXTRACTION_ASSETS_DIR="<extraction asset dir>" # optional: the catalogue snapshot the check before Write reads;
                                                         # unset, the app fetches the snapshot itself (below)
# hosted, behind a sign-in; each optional, and unset is as before:
export ESP_CROSS_ACCOUNT_ROLE_ARN="<role ARN>"           # these two together: every AWS call goes through this role,
export ESP_CROSS_ACCOUNT_EXTERNAL_ID="<external id>"     # assumed with this external id
export ESP_SIGNED_IN_USER_HEADER=X-Forwarded-User        # the request header that names the signed-in user: who confirms
export ESP_CONTACT="<whom to tell>"                      # whom the pages say to tell when something goes wrong
export ESP_SHOW_TECHNICAL=1                              # the technical views ("Run the viewer"); unset, they are hidden
AWS_PROFILE=roam-ai PYTHONDONTWRITEBYTECODE=1 .venv/bin/streamlit run app/main.py
```

Five settings make the app fit to run hosted, behind a sign-in; `app/hosted.py` reads them all. `ESP_SHOW_TECHNICAL` and `ESP_CONTACT` are under "Run the viewer".

- **One AWS session** (`hosted.session`) is behind the S3 client, the Athena client and the catalogue's fetch, all in `us-east-1`. With `ESP_CROSS_ACCOUNT_ROLE_ARN` and `ESP_CROSS_ACCOUNT_EXTERNAL_ID` both set it assumes that role with that external id (STS `AssumeRole`, called as the default chain's identity, the container's own; session name `esp-design-extraction-app`), with credentials botocore refreshes before they expire. With neither it is boto3's default chain, as before (`AWS_PROFILE`, or the other standard sources). With one and not the other the app starts on its plain set-up line, logs which setting is missing, and makes no AWS call. Neither value is in the code, and the role is assumed whenever both are set, whatever account the app itself runs in. The role is assumed when the app first builds its store; if that fails (no credentials for the app's own identity, the role refusing), the page is the plain line that the runs could not be read, the error goes to the log, and the next page load tries again.
- **Who confirms.** With `ESP_SIGNED_IN_USER_HEADER` set to a header's name, who confirms is that header's value among the session's request headers (Streamlit's `st.context.headers`: those of the browser's first request of the session), exactly as received, and nothing else: never STS, a query parameter, a form field or a cookie. With the header missing, empty or sent more than once, Write stays off and the page says why in plain words; no other name stands in. The value goes where `confirmed_by` goes (the request and each history step the confirmation adds, and from them the version and the row) and nowhere else: not into the log. Unset: with the two role settings set, Write is off in either mode, in plain words with the contact, and STS is not asked who confirms (a role's own session name would name no one); with neither set, the rule is as before: S3 mode, the STS caller's session name; local mode, `ESP_CONFIRM_OFFLINE_AS`. Local mode still writes only when `ESP_CONFIRM_OFFLINE_AS` is set, and with the header setting it then confirms as the signed-in user.
- **The pump catalogue.** In S3 mode with `ESP_EXTRACTION_ASSETS_DIR` unset, the app downloads the one object `esp-design-extraction/assets/universal_catalog.parquet` from `ESP_BUCKET` into a new temporary folder, points `ESP_EXTRACTION_ASSETS_DIR` at it, and checks it against `extraction/stage/MANIFEST.txt` through the loader every reader of it uses, as the Lambda's `fetch_assets` does (`hosted.fetch_catalogue`). A browser session asks once, at its first page; once the fetch has succeeded the variable is set, so a process fetches once. It reads nothing else under `assets/`. A failure (the object not there or not allowed, a hash that is not the manifest's) is logged, leaves nothing on disk, and is tried again by the next browser session; until then the review says in plain words that the pump catalogue could not be read, and Write stays off. With `ESP_EXTRACTION_ASSETS_DIR` set, nothing is fetched.

The credentials (the assumed role's, when the two role settings are set, which the app's own identity must then be allowed to assume with `sts:AssumeRole`; else `AWS_PROFILE`, or the other standard AWS sources) need these permissions on `roam-ds-assets`, and nothing more:

| Action | Resource | For |
|---|---|---|
| `s3:ListBucket` | the bucket, with `s3:prefix` under `esp-design-extraction/intake/` or `esp-design-extraction/runs/` | list uploads and runs |
| `s3:GetObject` | `esp-design-extraction/intake/*` and `esp-design-extraction/runs/*` | read an upload's labels and PDF, and a run's files |
| `s3:PutObject` | `esp-design-extraction/intake/*` | upload a PDF |
| `s3:PutObject` | `esp-design-extraction/confirmations/*` | write a confirmation request (`extraction.confirm` in S3 mode) |
| `s3:ListBucket` | the bucket, with `s3:prefix` under `esp-design-extraction/confirmations/`, `esp-design-extraction/well-entries/` or `esp-design-extraction/design-records/` | find a confirmation's result, the rows and a document's versions |
| `s3:GetObject` | `esp-design-extraction/confirmations/*`, `esp-design-extraction/well-entries/*` and `esp-design-extraction/design-records/*` | read a result, a row and a version |
| `s3:GetObject` | `esp-design-extraction/assets/universal_catalog.parquet`, and nothing else under `assets/` | fetch the pump catalogue snapshot, when `ESP_EXTRACTION_ASSETS_DIR` is unset |

The upload form's well lists also need Athena in `us-east-1`: the app calls `athena:StartQueryExecution`, `athena:GetQueryExecution`, `athena:GetQueryResults` and, for a query still running after 120 s, `athena:StopQueryExecution`, in the workgroup `ESP_ATHENA_WORKGROUP` names, with whatever the results location and the two data sources' connectors require.

## Run it in a container

`container/` turns the app into an app folder for the company's container platform, which serves it at `/enterprise/esp-design-extraction` behind its sign-in. It holds:

- `Dockerfile`: the platform's Streamlit pattern (`python:3.12-slim`, port 80), started from `/app` on `app/main.py` so that `.streamlit/config.toml` applies and the fonts are served. `/app` in the image holds `app/`, `extraction/` and `.streamlit/config.toml`, and nothing else.
- `requirements.txt`: this folder's `requirements.txt` less `pytest` and `reportlab`, with the same pins (`tests/test_container.py` keeps the two in step).
- `.dockerignore`: caches and editor files.
- `app.config.json`, a template: the platform's app config, with the settings of "Run the app against S3" for a hosted app (S3 mode, the bucket and prefixes as the stack gives the Lambda, the sign-in header `X-Forwarded-User`; `ESP_SHOW_TECHNICAL` is not set) and `{{…}}` placeholders for the owner, the contact, and the data role's ARN, external id and account. Its `iam` block asks for `sts:AssumeRole` on that role and nothing else: what the role may do is the table above, granted where the role is defined.
- `build.py` and `run_local.sh`, below.

**Build the folder.**

```bash
.venv/bin/python container/build.py --target "<platform repo>" --contact "<whom engineers tell>" --owner "<the app's owner>"
```

It writes `<platform repo>/apps/enterprise/esp-design-extraction/`, replacing that folder and nothing else: `app/`, `extraction/` and `.streamlit/config.toml` as git knows them (no cache, nothing ignored), `Dockerfile`, `requirements.txt` and `.dockerignore` as they are, `app.config.json` with its placeholders filled, and `SOURCE.txt` (this repository's remote, the commit, the time, the shipped paths). The contact and the owner come from the command line; the role's ARN, external id and account from the platform's `cdk.json`, under `context.master` (`accountId`, `crossAccountDataRole.roleName` and `.externalId`). It writes nothing when a placeholder would be left, a value is missing or empty, or a shipped path has uncommitted changes: **the folder that goes into a pull request is built from a committed tree**, and its `SOURCE.txt` names that commit. `--local-test` builds from the files as they are, and `SOURCE.txt` then says `uncommitted: local test only`: such a folder is for this machine, never for a pull request. The same source gives the same files, `SOURCE.txt`'s time apart. No network, no AWS.

**Run it on this machine.**

```bash
container/run_local.sh "<platform repo>/apps/enterprise/esp-design-extraction" "<AWS profile>" [port]
```

It builds the image from that folder for `linux/amd64` and runs it, reachable from this machine only, at the address it prints (port 8501 unless one is given). The container runs as the developer, not as the platform: it gets the folder's settings less four, and the script says so before it starts. The two role settings are left out: on the platform the app assumes the data role, here it uses the profile's own credentials. `ESP_SIGNED_IN_USER_HEADER` is left out: nothing in front of a local container signs anyone in, so who confirms is the profile's own session name. `ESP_ATHENA_OUTPUT_LOCATION` is left out: the well lists use the app's default results location, not the platform's. The AWS CLI reads the credentials into the script's environment and Docker passes them on by name, so they are never written to a file or put on a command line. They are temporary: when they expire, stop the container and run the script again. Without a profile it builds and runs nothing.

**Its size.** `cpu` 512 and `memoryLimitMiB` 1024: in the image, on a local store, one review of a ten-page scan with every page seen peaked at 268 MiB, and 1024 is the smallest memory Fargate takes that is at least twice that.

## Detect survey

`tools/detect_survey.py` runs Detect alone over every PDF in a folder, at any depth: no model, no AWS. It writes `survey.csv` (per PDF: path, SHA-256, organisation as the first path segment, size, pages, producer and creator, text-layer characters, Detect's result and its required-page result, every family's page-1 markers found and, where any are, its required page roles found, and a layout fingerprint for a document with no family) and `summary.md` (the totals, one row per unique document named `<organisation>/#<n>`, shared layouts, exceptions). The CSV holds paths, which carry well names, so the output folder must be outside this folder. `--corpus` checks the totals against the corpus results (46 documents in the six families, one `IMAGE_ONLY`, one `UNKNOWN_TEMPLATE`) and exits 1 when they differ.

```bash
export ESP_SURVEY_DIR="<folder of PDFs>" ESP_SURVEY_OUT="<output dir>" ESP_WELL_LIST_PATH="<well list CSV>"
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python tools/detect_survey.py            # add --corpus on the corpus dir
```

Page-1 headings in the summary are rows set larger than the body text and in one font, with no digit and no client from the well list; a row that mixes fonts is a label with its value, which can name a person or a well.
