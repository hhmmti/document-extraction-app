# ESP design extraction: AWS stack

One Lambda in the datascience account (`640168431387`, `us-east-1`) runs the design-document extraction pipeline when a PDF lands under `s3://roam-ds-assets/esp-design-extraction/intake/`. The stack is CDK (Python), stack `EspDesignExtractionStack`. The function ships as a container image. Its handler, `lambda_function.py` at the lab root, runs the pipeline on one intake PDF and writes the run's folder under `runs/`; its docstring lists the steps. A second Lambda from the same image, the confirmation writer (`lambda_function.confirm_handler`), runs when a confirmation request lands under `confirmations/`: it writes the document's design record under `design-records/` and one row of the well-entries table under `well-entries/` (the lab README's "Confirming an entry"). Athena reads the rows through the Glue table `esp_design_extraction.well_entries` and each well's current entry through the view `well_entries_current`. A third, the product's starter (`lambda_function.product_upload_handler`), runs when the ESP product pushes a design PDF into the stack's own bucket `esp-design-extraction-product-uploads-640168431387`: it puts the PDF at `intake/<run_id>.pdf` with its labels, which starts the extraction (Intake, below). Two more run the image route, which transcribes a scan the extraction could not read. The route's starter (`lambda_function.transcription_start_handler`) runs when the extraction puts a transcription request under `transcriptions/`, and starts one ECS task on Fargate, from an image of its own (`image_route/task.py`), which reads the scan's pages through Bedrock, builds the transcription and puts it at `intake/<run_id>.pdf`. The watcher (`lambda_function.transcription_watch_handler`), called by an EventBridge rule for each of the route's tasks that stops, ends a request whose task did not.

**Why the triggers cannot loop.** The extraction's fires only for `.pdf` keys under `intake/`, and that function can write only under `runs/` and a transcription request's `request.json`. The writer's fires only for keys ending `request.json` under `confirmations/`, and the writer can write only under `design-records/`, under `well-entries/` and to `confirmations/<id>/result.json`. The product's starter's fires only for `.pdf` keys in the product-upload bucket, which no function can write, and the product's starter writes only `intake/<run_id>.pdf`, which starts the extraction: that is what it is for. The route's starter's fires only for keys ending `request.json` under `transcriptions/`, and it and the watcher write only `result.json` beside a request. No function can write a key that its own trigger, or the writer's, matches. The image route is the one loop, and it closes once: the extraction's request starts the task, the task's transcription is an intake upload, which the extraction runs, and the extraction asks no transcription for an upload labelled `transcribed-from`, as every transcription the task puts is.

**CDK's helper Lambda.** The stack does not own `roam-ds-assets`, so CDK sets the notification through a custom resource backed by its own small Lambda (`BucketNotificationsHandler…`). That Lambda runs only when the stack is deployed, updated or deleted. Its role has `s3:GetBucketNotification` and `s3:PutBucketNotification` on this bucket only, plus the AWS managed policy `AWSLambdaBasicExecutionRole` for its own logs. It reads the bucket's current notification configuration and keeps every notification it did not create, including any EventBridge setting. It adds or removes only this stack's notifications. The same helper sets the product-upload bucket's notification, a second custom resource with its own policy (`s3:PutBucketNotification` on that bucket only); the stack owns that bucket, so the helper writes its whole configuration.

**Retained on delete.** The run-log table, the six log groups, the product-upload bucket (with every version of every push), the Glue database, the table and the view survive a stack deletion, so run history, logs and the table's definition are kept and must be removed by hand if ever wanted. The functions, the image route's VPC, security group, cluster, task definition and rule, their roles, the helper, this stack's notifications and the product-upload bucket's policy are removed, so the product can no longer put there. The helper also leaves its own log group, `/aws/lambda/<generated name>`, with no expiry, outside the stack. The bucket and its objects are never touched. Both images stay in the bootstrap repository.

## Build and test

Prerequisites: Python 3.12 and Node.js; the tests and `synth` need nothing else. `app.py` takes the account from `AWS_ACCOUNT_NUMBER` and the region from `AWS_DEFAULT_REGION`, as the ESP monorepo's CDK apps do. It has no defaults: if either is unset it exits, naming both.

```bash
cd cdk
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python build_lambda.py                 # stages the two image contexts, build/lambda/ and build/task/
.venv/bin/python -m pytest                        # template, app and workflow tests; no build, no AWS
AWS_ACCOUNT_NUMBER=640168431387 AWS_DEFAULT_REGION=us-east-1 PATH="$PWD/.venv/bin:$PATH" npx aws-cdk@2.1144.0 synth --no-notices
```

The image starts from `public.ecr.aws/lambda/python`, pinned to a dated tag in `Dockerfile`. It installs `requirements-lambda.txt`, in which every package is pinned to the versions the pipeline's tests ran, into the function directory, which Lambda searches first, so the pinned boto3, botocore and urllib3 are used rather than the base image's copies. It holds the handler and the whole pipeline package, including its contracts, prompts and pricing table, but not the data assets.

The task's image, from `Dockerfile.task`, starts from the same pinned base and installs `requirements-task.txt`: the Lambda's packages and the two the skill's build and the hand-back's check need, pypdf and reportlab. It holds the handler module, the pipeline package, `image_route/`, the skill's folder `skills/transcribe-design-scan/`, and of the app only `__init__.py` and `transcription.py`. Its entrypoint is `python -m image_route.task`, in place of Lambda's.

## Intake

A run starts when a PDF lands at `intake/<run_id>.pdf`, the run id in the pipeline's format (`YYYYMMDDTHHMMSSZ-<8 hex>`). The object carries four metadata labels, each percent-encoded UTF-8: `organization-id`, `well-id`, `source-name` (a plain file name) and `sha256` (the PDF's, lower-case hex). The function creates `runs/<run_id>/run.json` as `running` only if it does not exist, so a repeated event stops there. It rewrites `run.json` last, after the rest of the folder, as `succeeded` or `failed`. A run that cannot finish keeps `running` and reads as stale after its `deadline_at`.

The run log holds one row per run, shaped as the ESP product's file-upload pipeline row (`type` `PIPELINE_EXECUTION`): written `RUNNING` once the labels are read, then updated in place to `SUCCEEDED` or `FAILED`. A failure before that (a key that is not a run id, a failed create, bad labels) writes one `FAILED` row instead: under the organisation `_unknown` when its label was not read or does not decode, and with the pipeline execution id `ADHOC#<request id>` when the key holds no run id. A duplicate writes none. A missing or undecodable label, or a hash mismatch, fails the run with `INTAKE_INVALID`. Anything unexpected fails it with `INTERNAL_ERROR`, and the trace goes to the log group.

An upload carries four labels more when the product's starter made it, from a PDF the ESP product pushed into `esp-design-extraction-product-uploads-640168431387` at `<dev|prd>/<organization_id>/well-documents/<well_id>/esp_design/<file>.pdf`: `origin`, `environment`, `uploaded-by` and `pushed-from` (the lab README's "Run the viewer"). The extraction reads only the four; the app and the writer read the others. The product's starter's run id comes from the event (its second, and a hash of the bucket, the key and the version), so a repeated event finds its upload there and stops.

An upload the image route's task made carries the original's four labels, with `source-name` the transcription's file name and `sha256` its hash, each optional label the original carries, and `transcribed-from`, the original run id. Its run id is fresh, in the upload form's pattern.
