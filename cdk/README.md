# ESP design extraction: AWS stack

One Lambda in the datascience account (`640168431387`, `us-east-1`) runs the design-document extraction pipeline when a PDF lands under `s3://roam-ds-assets/esp-design-extraction/intake/`. The stack is CDK (Python), stack `EspDesignExtractionStack`. The function ships as a container image. Its handler, `lambda_function.py` at the lab root, runs the pipeline on one intake PDF and writes the run's folder under `runs/`; its docstring lists the steps.

## What this deploys

| Resource | Name | Settings |
|---|---|---|
| Lambda function | `esp-design-extraction` | container image on the AWS Lambda Python 3.12 base image, x86_64, command `lambda_function.lambda_handler`, 900 s timeout, 2048 MB, reserved concurrency 1 (one run at a time), asynchronous retries 0 (a failed run is recorded, not re-run) |
| Log group | `/aws/lambda/esp-design-extraction` | 90-day retention |
| IAM role | generated by CDK | the function's own role; inline statements only, no managed policies |
| DynamoDB table | `esp_design_extraction_logging` | the run log, in the layout of the ESP product's `esp_logging_v2`: key `organization_id` + `timestamp`; indexes `uuid` (on `uuid`), `pipeline_execution_id_timestamp`, `organization_id_type_timestamp` and `status_timestamp` (each on its attribute and `timestamp`), all attributes projected; on demand; point-in-time recovery; no TTL and no stream. One row per run: written `RUNNING`, then updated to `SUCCEEDED` or `FAILED` |
| S3 trigger | on the existing bucket `roam-ds-assets` | object created, prefix `esp-design-extraction/intake/`, suffix `.pdf` |
| Container image | in the account's CDK bootstrap repository, `cdk-hnb659fds-container-assets-640168431387-us-east-1` | built and pushed by `cdk deploy`; not a stack resource |

Environment variables: `ESP_BUCKET`, `ESP_INTAKE_PREFIX`, `ESP_RUNS_PREFIX`, `ESP_ASSETS_PREFIX`, `ESP_RUN_LOG_TABLE`, `ESP_INFERENCE_PROFILE_ID`.

**The function's permissions.** These are all of them: no wildcard actions and no `*` resources.

| Actions | Resource | Why |
|---|---|---|
| `s3:GetObject` | `roam-ds-assets/esp-design-extraction/intake/*` | read the uploaded PDF and its metadata |
| `s3:GetObject` | `roam-ds-assets/esp-design-extraction/assets/*` | read the data assets the pipeline hash-checks |
| `s3:PutObject` | `roam-ds-assets/esp-design-extraction/runs/*` | write the run's folder |
| `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream` | inference profile `us.anthropic.claude-opus-5-5` | the run's one streaming model call |
| the same two | `anthropic.claude-opus-5-5` in us-east-1, us-east-2 and us-west-2, only when called through that profile | the US profile can route a request to any of the three regions |
| `dynamodb:PutItem`, `dynamodb:UpdateItem` | the run-log table | the run's row: written once the labels are read, updated when the run ends |
| `logs:CreateLogStream`, `logs:PutLogEvents` | its own log group | the run's trace |

The bucket uses SSE-S3, so no KMS permission is needed. S3 may invoke the function only from this bucket and this account.

**Why the trigger cannot loop.** It fires only for `.pdf` keys under `intake/`. The function can write only under `runs/`, so nothing it writes can match the trigger.

**CDK's helper Lambda.** The stack does not own `roam-ds-assets`, so CDK sets the notification through a custom resource backed by its own small Lambda (`BucketNotificationsHandler…`). That Lambda runs only when the stack is deployed, updated or deleted. Its role has `s3:GetBucketNotification` and `s3:PutBucketNotification` on this bucket only, plus the AWS managed policy `AWSLambdaBasicExecutionRole` for its own logs. It reads the bucket's current notification configuration and keeps every notification it did not create, including any EventBridge setting. It adds or removes only this stack's notification.

**Retained on delete.** The run-log table and the log group survive a stack deletion, so run history and logs are kept and must be removed by hand if ever wanted. The function, both roles, the helper and this stack's notification are removed. The bucket and its objects are never touched. The image stays in the bootstrap repository.

## Build and test

Prerequisites: Python 3.12 and Node.js; the tests and `synth` need nothing else. `app.py` takes the account from `AWS_ACCOUNT_NUMBER` and the region from `AWS_DEFAULT_REGION`, as the ESP monorepo's CDK apps do. It has no defaults: if either is unset it exits, naming both.

```bash
cd cdk
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python build_lambda.py                 # stages the image context in build/lambda/
.venv/bin/python -m pytest                        # template, app and workflow tests; no build, no AWS
AWS_ACCOUNT_NUMBER=640168431387 AWS_DEFAULT_REGION=us-east-1 PATH="$PWD/.venv/bin:$PATH" npx aws-cdk@2.1144.0 synth --no-notices
```

The image starts from `public.ecr.aws/lambda/python`, pinned to a dated tag in `Dockerfile`. It installs `requirements-lambda.txt`, in which every package is pinned to the versions the pipeline's tests ran, into the function directory, which Lambda searches first, so the pinned boto3, botocore and urllib3 are used rather than the base image's copies. It holds the handler and the whole pipeline package, including its contracts, prompts and pricing table, but not the data assets.

## Deploy

Only through the GitHub Actions workflow `ds-deploy-esp-design-extraction.yaml`, never from a laptop.

Prerequisites:

- the `DS_*` secrets available to the repository: `DS_AWS_ACCESS_KEY_ID`, `DS_AWS_SECRET_ACCESS_KEY`, `DS_AWS_DEFAULT_REGION` (it must be `us-east-1`) and `DS_ACCOUNT_NUMBER`;
- the workflow in the repository root's `.github/workflows/`, both on `main` (GitHub only offers a dispatch workflow that is on the default branch) and on the branch being deployed.

To run it: Actions → **DS Deploy ESP Design Extraction** → Run workflow → pick the branch → tick the confirmation.

The workflow stops unless the region is `us-east-1` and the credentials are for `640168431387`. Then, in `esp_design_extraction/cdk`, it installs `requirements.txt`, runs `build_lambda.py` and then `cdk deploy --require-approval never`, with the same CDK CLI version as the synth above. `cdk deploy` builds the image with the runner's Docker, for `linux/amd64`, and pushes it to the bootstrap repository. A second run waits for a running one rather than overlapping it.

Before deploying, check two things on `roam-ds-assets`. First, the bucket policy must not deny this role; it has not been reviewed yet. Second, no existing object-created notification may overlap the `intake/` prefix, because S3 rejects overlapping notification rules.

## Install the workflow

Copy `cdk/workflows/ds-deploy-esp-design-extraction.yaml` to `.github/workflows/` at the repository root, and keep the two copies identical.

## Before the first run

The four data assets go to `s3://roam-ds-assets/esp-design-extraction/assets/`: `alias-evidence-v1.json`, `m2-d31-seed-aliases.csv`, `universal_catalog.parquet` and `m1-field-inventory.csv`. They are not in the image. Each must match the SHA-256 recorded in `extraction/stage/MANIFEST.txt` (the field inventory: `extraction/assets/MANIFEST.txt`). A missing or changed asset fails the run with `ASSET_INVALID`.

## Intake

A run starts when a PDF lands at `intake/<run_id>.pdf`, the run id in the pipeline's format (`YYYYMMDDTHHMMSSZ-<8 hex>`). The object carries four metadata labels, each percent-encoded UTF-8: `organization-id`, `well-id`, `source-name` (a plain file name) and `sha256` (the PDF's, lower-case hex). The function creates `runs/<run_id>/run.json` as `running` only if it does not exist, so a repeated event stops there. It rewrites `run.json` last, after the rest of the folder, as `succeeded` or `failed`. A run that cannot finish keeps `running` and reads as stale after its `deadline_at`.

The run log holds one row per run, shaped as the ESP product's file-upload pipeline row (`type` `PIPELINE_EXECUTION`): written `RUNNING` once the labels are read, then updated in place to `SUCCEEDED` or `FAILED`. A failure before that (a key that is not a run id, a failed create, bad labels) writes one `FAILED` row instead: under the organisation `_unknown` when its label was not read or does not decode, and with the pipeline execution id `ADHOC#<request id>` when the key holds no run id. A duplicate writes none. A missing or undecodable label, or a hash mismatch, fails the run with `INTAKE_INVALID`. Anything unexpected fails it with `INTERNAL_ERROR`, and the trace goes to the log group.
